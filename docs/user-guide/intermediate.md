# User guide: Intermediate

[New to GitHub](beginner.md) · **Intermediate** · [Advanced](advanced.md)

**Who this is for:** You can find your way around a repository and want to judge a project, contribute to one or look after your own.

**By the end:** Judge whether a project is well looked after, take part through issues and pull requests, and know what good looks like in government.

## Steps

1. Check how well a project is looked after: README, licence, code owners, recent activity and automated checks. (in the catalogue: *practice* view)
2. Compare a project with the GDS Way and the Service Manual's guidance on open code. (in the catalogue: *gdsway* view)
3. Find projects that publish a website with GitHub Pages, and who runs them. (in the catalogue: *pages* view)
4. Explore projects by topic and by organisation to find work you could reuse rather than rebuild. (in the catalogue: *topics* view)
5. Raise an issue or propose a change with a pull request, following the GitHub flow.
6. Use the analytics dashboard to see patterns across the estate. (in the catalogue: *insights* view)

## Words you'll meet

- **Branch:** A separate line of work, so changes can be made and reviewed without affecting the main version.
- **Pull request:** A proposal to merge a branch's changes, with review and discussion before they go in.
- **Fork:** Your own copy of someone else's repository, used to propose changes when you can't change theirs directly.
- **CODEOWNERS:** A file naming who must review changes to which parts of a repository.
- **Licence:** Says how others may use the code. Government code is usually MIT; content is usually under the Open Government Licence.
- **GitHub Pages:** A website published straight from a repository.
